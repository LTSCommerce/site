**Auditor**: Fable independent audit pass (third review overall, after the pre-flight and Phase 1/2 Opus reviews).
**Date**: 2026-07-10
**Scope**: PLAN.md, preflight-opus-review.md, phase1-concept-report.md, phase1-opus-review.md, phase2-design.md, phase2-opus-review.md, cross-checked against real source in `/workspace`, `/workspace/untracked/repos/php-qa-ci`, and `/workspace/untracked/ec-site`.

## Verdict

**NOT READY to proceed to Phase 3 as it stands — but close.** The plan is unusually well-researched and its factual baseline is genuinely solid (every one of my 14 spot-checks against real source held up, see Appendix). However:

1. The "fixed" blocking finding from the Task 2.7 review is **not actually fixed**: `resolveEslintConfig()`'s merge-not-replace semantics do not deliver the estate-wide guarantee they claim, because ESLint flat config resolves rule severity **last-entry-wins** — an appended project config entry can silently set any Tier A rule to `'off'`. "Can only add, never replace" is factually wrong about flat config: appending *is* replacing, per rule. Both Opus passes missed this; the review's own suggested fix contains the same error (Finding B1).
2. phase2-design.md carries a **stale self-contradiction** introduced by the revision pass itself (§3 vs §7 risk 4 on testing-tool peerDeps) (S1).
3. The Task 3.0 sign-off gate is a **paper gate** with inconsistent breadth wording and no required evidence artifact, and there is at least one easy accidental route-around already designed in (S2).
4. Phase 4 has an **unbudgeted work item hiding in a success criterion**: the repo has zero test files, Task 4.6 adds a test gate to CI, and no task anywhere budgets writing the first test suite (S3).
5. The plan is **too big** and should be pre-split rather than relying on a mid-flight fallback (S5).

All of the blocking/significant items are bounded design-document fixes, not rethinks. Recommended sequence: fix B1, S1, S2 in the design docs and PLAN.md (roughly a day of editing, no new research), add the S3 task and the S5/S6 re-scoping decisions, **then** run Task 3.0. Do not start Task 3.0 before S2 is fixed, because the gate's own definition is what needs correcting.

## Blocking findings

### B1. The `resolveEslintConfig()` fix does not resolve the Task 2.7 blocking finding — it moves it one level down

The Task 2.7 review correctly found that a wholesale-replace cascade lets a consumer silently drop the Tier A core/CDD tier. The applied fix (phase2-design.md §2.4/§4) is:

```
return [...base, ...projectAdditions]   # MERGE — project file can only ADD, never replace
```

This prevents *array-level* replacement but not *rule-level* replacement. ESLint flat config is explicitly last-match-wins per rule: a later config entry with `files: ['**/*.tsx'], rules: { 'ts-qa/no-ad-hoc-html': 'off' }` overrides the earlier Tier A entry. That is not a hypothetical — **ec-site's own `eslint.config.js` relies on exactly this semantics**, turning its flagship CDD rule off in a later entry (`'local-rules/no-html-in-pages': 'off'` for `src/pages/design-guidelines/**`, verified at line 835). So under the "fixed" design, a consumer's `tsQaConfig/eslint.config.js` can still silently disable any Tier A rule, one rule at a time, with no logging and without touching the documented opt-out surface (`cdd-exclusions.json` / `TSQA_DISABLE_CDD`). The guarantee that justified the entire §4 "ts-qa owns the config" decision remains trivially bypassable.

The design's claim "a project's file … is never given the chance to replace `base`" conflates *which file object is loaded* with *which rule severity wins*. The Task 2.7 review's own fix text ("may only add rules (force-merged after the base)") shares the blind spot, so the revision faithfully implemented a broken fix.

**Two failure modes, in opposite directions:**

- **Guarantee weaker than claimed**: per-rule silent disablement is open (above).
- **Legitimate-override path missing**: the documented opt-out covers only the CDD tier. Tier A contains eight non-CDD rules (`no-eslint-disable`, `require-explicit-type-annotations`, etc.) with **no sanctioned override at all** — yet real projects demonstrably need per-file rule-offs: this very repo's `eslint.config.js` turns two rules off for `articles.ts` (lines 128–138, verified), and ec-site needed its flagship CDD rule off for its component-demo page. A project with a genuine need (generated code, a demo page, a data file) has no legitimate path and will use the accidental one — at which point the accidental path cannot be closed without breaking them.

**Fix**: `resolveEslintConfig()` must post-process the merged array: detect project entries that touch Tier A rule IDs (any severity change, not just `'off'`) and either (a) hard-reject with a message routing the consumer to a *newly defined* sanctioned per-rule/per-glob exemption mechanism that is logged on every run (extend `cdd-exclusions.json` into a general `tier-a-exemptions.json` with a required per-entry justification string), or (b) allow but loudly log every effective Tier A downgrade in every run's output so it can never be *silent*. Option (a) matches the SensitiveParameter precedent (opt-out is narrow, named, and visible) and also answers the legitimate-override question the current design ignores. Alternatively, honestly re-scope the claim: "Tier A is default-on and tamper-evident, not tamper-proof" — but then Decision/Task 2.4's rationale text must be rewritten to match.

## Significant findings

### S1. phase2-design.md contradicts itself on the testing-tool peerDep decision — a revision-pass regression

§3's dependency table now says `vitest`/`@playwright/test`/`@stryker-mutator/core` are **peerDependency**, marked "Resolved (was left open pending Phase 3 in an earlier draft)". But §7 Open Risks item 4 still reads: "`vitest`/`@playwright/test` peerDependency-vs-bundled is **explicitly left as a Phase 3 build decision** (§3) … does not resolve it." Both statements cite §3 and cannot both be true. PLAN.md's Task 2.7 entry claims this non-blocking finding was "resolved inline" — it was, in §3, but the revision pass failed to update §7, leaving the design in a state where a Phase 3 build agent reading the risk register concludes the decision is still open. One-line fix: strike or rewrite §7 item 4 (mirror the strikethrough treatment items 1 and 2 received).

### S2. The Decision 5 / Task 3.0 sign-off gate is a paper gate with an accidental route-around already designed in

Three problems:

1. **No evidence artifact.** Task 3.0 says "obtain the maintainer's explicit sign-off" but defines no record of it. In an agent-executed plan, a gate with no checkable artifact is satisfiable by an agent asserting it happened. Fix: Task 3.0's acceptance criterion should be a dated file in this plan folder (e.g. `ec-site-lift-signoff.md`) quoting the maintainer's actual words and the agreed lift/adapt/drop boundary, referenced from PLAN.md's Decision 5.
2. **Inconsistent gate breadth.** Task 3.0 says the gate blocks "any other Phase 3 task"; PLAN.md's Notes & Updates says Phase 3 is "blocked on Task 3.0 … before any scaffolding **that touches ec-site-derived rules** begins" — materially narrower. And phase2-design §2.3 puts `cache.ts` ("lifted near-verbatim from ec-site's `scripts/lib/cache.ts`") inside the Task 3.1/3.2 orchestrator scaffold. An agent following the Notes wording would scaffold `cache.ts` before sign-off because it is not a "rule" — yet it is exactly the kind of ec-site code Decision 5 (which names "rules, meta-rules, **cache library**, or orchestrator scripts") gates. Fix: make the wording uniform (gate blocks all lift of any ec-site-derived code — rules, meta-rules, cache library, orchestrator patterns-as-code) and note explicitly that Tasks 3.1/3.2 contain gated content via `cache.ts`.
3. **Sign-off scope must explicitly cover public source visibility.** Decision 6 makes the repo public at Task 3.6 — *before* Phase 5's npm-publish decision. Decision 5's wording ("relicensed/republished under `@longtermsupport`") arguably covers this, but the sign-off record should state it explicitly, since "OK to publish a package eventually" and "OK for adapted private code to sit in a public GitHub repo next month" are different consents a maintainer could plausibly split.

### S3. Zero tests: a success criterion with no task behind it

The measured baseline (PLAN.md, verified): zero test files, `vitest run` exits 1 with "No test files found." Task 4.6 adds a **test gate** to CI for the first time; the success criteria require the "zero tests" baseline "resolved." But no task in any phase budgets *writing* an initial test suite. The options are: (a) the pipeline's Phase 4 passes vacuously via `passWithNoTests`-style config — which makes the new CI "test gate" a no-op and quietly betrays the success criterion; or (b) someone writes the first real tests for a 17-component/5-page app plus every new Task 4.5 catalogue component — real, unbudgeted work that belongs in the same league as the catalogue itself. The plan already shows the discipline of budgeting the catalogue explicitly (Decision 4); the same discipline is missing here. Fix: add an explicit Task 4.x ("author the initial Vitest/Playwright suite sufficient for the gate to be meaningful — define the minimum bar") or consciously re-scope the success criterion to "test *gate wired and green*, initial suite deferred to a named follow-on plan."

### S4. `no-eslint-disable` is dormant in ec-site — its pedigree is overstated, and it collides with the CDD suppression-governance language the design plans to reuse

Verified: `eslint-rules/no-eslint-disable.js` exists in ec-site, but the string "eslint-disable" appears **nowhere** in ec-site's `eslint.config.js` — the rule is neither imported nor registered (ec-site registers rules individually, e.g. `no-placeholder` at lines 36/300/385, so there is no dynamic loader that could pick it up). Two consequences:

1. The report/design framing of this rule as the "strongest possible signal … three independent cross-project precedents" always-on Tier A candidate overstates it: the file exists but has apparently never run in anger in ec-site. Existence was spot-checked by the Phase 2 review ("every ec-site rule file named in §4's tier tables exists"); *registration* was not. At least re-verify the rule works before promoting it to always-on.
2. **A direct design contradiction nobody has caught**: phase2-design §4 keeps `no-orphaned-grid-items`' suppression-governance language for "reuse verbatim in the CDD docs" — "Only project maintainers can AUTHORIZE exceptions **via suppression comment**" (verified, `no-orphaned-grid-items.js:23`). But Tier A's always-on `no-eslint-disable` **bans all suppression comments repo-wide**. A governance policy whose escape hatch is a suppression comment cannot coexist with a total suppression-comment ban. This may be precisely *why* ec-site never registered `no-eslint-disable`. ts-qa-ci must pick one: an allowlisted/justified-suppression mechanism in `no-eslint-disable`, or a different CDD exception mechanism than suppression comments (the glob-exclusion file), and drop the "verbatim" reuse.

### S5. The plan is too big, and I will say so plainly since nobody else has

This single plan contains what are honestly three plans:

1. **The ts-qa-ci package**: orchestrator CLI, 4-phase pipeline, config cascade, ~10 tool runners, ~25 rules across three tiers including two novel CDD rules, full docs set, Node deploy tooling, CI install mechanism, GitHub repo.
2. **lts-commerce-site quality remediation**: baseline fixes, the repo's **first-ever tests** (S3), first-ever CI quality gates, Claude-integration deploy verification against a live hooks-daemon.
3. **A design-system build**: a variant-prop component catalogue from zero (0 CVA usage today, verified) plus migration of 259 `className` literals (verified exact) and ~200 raw JSX tags onto it.

The risk table's mitigation for (3) is a *mid-flight fallback* ("if it balloons, split it out"). Ballooning is not a risk here; it is the base case — building a variant catalogue for a site with no variant infrastructure, then migrating every styling touchpoint, is a full plan by this repo's own standards regardless of how smoothly it goes. The fallback should be exercised **now**: pre-split Task 4.5's catalogue-build + migration into its own numbered plan that this plan blocks on for its CDD-Tier-B success criterion, and re-scope this plan's Phase 4 CDD deliverable to "Tier A `no-ad-hoc-html` enforced + Tier B implemented and validated against the pilot component(s)". Similarly, Task 3.4/4.8 (Claude Code deploy tooling) is orthogonal to the QA pipeline and is the plan's most externally-coupled work (it codes against the hooks-daemon's project-handler contract, owned by an upstream dependency) — a clean candidate to defer to a follow-on. Note also the optics problem: PLAN.md shows 2 of 5 phases complete, but Phases 1–2 were research/design; the overwhelming majority of effort is still ahead. That is not a flaw, but it should temper any "60% remaining" reading.

### S6. Task 3.3's variant-API enforcement rule cannot actually be completed in Phase 3

The rule enforces "every styleable component must expose typed variant props" — but the conventions it enforces (naming, typing, exhaustiveness shape) are defined by the catalogue that only comes into existence at Task 4.5, and phase2-design §7 risk 7 already admits its "mechanics are entirely unspecified" with no ec-site precedent to adapt (ec-site's CVA usage is a single pilot component — verified: `cva(` appears in exactly one file). The plan acknowledges 3↔4 interleave in general terms, but this specific sub-task is not an interleave — it is strictly downstream of Phase 4.5's design decisions. Move it explicitly into (or after) Task 4.5's sub-phases, or mark it "authored during Phase 4" in Task 3.3, so a Phase 3 agent doesn't attempt to invent the variant convention ahead of the catalogue. (If S5's pre-split is adopted, this rule moves to the split-out plan with the catalogue.)

### S7. Bundled Prettier vs the consumer's own Prettier: an unexamined format ping-pong risk

phase2-design §3 bundles `prettier` inside ts-qa-ci ("version pinned … for reproducibility") while this repo keeps its own `prettier` devDependency and `format`/`format:check` scripts (verified). Two Prettier instances at different versions can disagree on output; the dogfood repo would then oscillate — `npm run format` writes one shape, `ts-qa` (Phase 1, writable mode) rewrites it, CI's format gate flags whichever ran second. The §3 reasoning ("no consumer coupling — Prettier output doesn't need to match a consumer instance") is exactly wrong for a consumer that *also* runs its own Prettier, which the dogfood target does. Fix: either peerDep Prettier too, or make Task 4.1 remove/alias this repo's own Prettier scripts to route through `ts-qa`, and say which in the design.

The plan's habit of measuring before claiming is its strongest feature.
- **P2. The pre-flight review earned its keep.** The ec-site discovery and the CI-premise correction were both load-bearing and both correctly folded into the plan; the correction ("adds gates, doesn't consolidate") survives consistently through PLAN.md, both reports, and the design.
- **P3. Decision 3 (JSX-only CDD scope) is soundly grounded** on two independent legs: the technical fact that a JSX AST rule cannot see inside template literals, and ec-site's precedent of treating article prose as a separately-governed surface. The success criteria are correctly redefined against the JSX surface.
- **P4. The §6 CI install mechanism is concrete and correct**: SHA-pinned git dependency, committed `dist/` to dodge the `prepare` flakiness, the peerDep-not-installed trap flagged, a documented fallback with honest caveats. This was a hard blocker in the first draft and is now the plan's most build-ready section.
- **P5. Honest uncertainty flagging is consistent**: Phase 1's "not covered by any research section" admissions, §7's risk register, and Decision 5's "flag, don't resolve unilaterally" discipline are all genuine, not decorative.
